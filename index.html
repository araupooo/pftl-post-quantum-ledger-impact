PFTL Post-Quantum Ledger Impact Assessment

Reproducible assessment of how ML-DSA-44/65/87 and SLH-DSA signatures affect transaction size, throughput, fees, validator storage, and spam resistance on a ledger of the XRPL family (postfiatd), versus Ed25519/secp256k1. Labels: MEASURED (produced by this harness), MODEL (calibrated from published measurements), DERIVED (arithmetic shown), ASSUMED (stated modelling input), UNVERIFIED (not confirmed). Full detail, sources, and the claim-to-evidence index are in the companion files (findings.md, sources.md, claims.md, model.md, mitigations.md, measurements.md, limitations.md). Reproduce with python3 scripts/run_all.py — 38/38 checks pass.

Headline results

  • A model ML-DSA-65 transaction is 5,461 bytes vs 297 bytes for Ed25519 — 18.4x larger (DERIVED). The signature alone is 3,309 bytes vs 64 bytes — 51.7x (FIPS 204 Table 2; RFC 8032 §7).
  • At 1,500 TPS, ML-DSA-65 transactions add ~708 GB/day to the ledger stream vs ~38.5 GB/day for Ed25519 (DERIVED).
  • Fees are count-based, not byte-based: a 3,309-byte ML-DSA-65 signature costs the same 10 drops as a 64-byte Ed25519 signature at base load. Spam per ledger megabyte costs 1,830 drops via ML-DSA-65 vs 33,670 drops via Ed25519 (DERIVED).
  • Verification is not the bottleneck: calibrated MODEL throughput is ~16,667 ML-DSA-65 verifies/second per core, vs ~18,868/second derived for Ed25519.
  • postfiatd contains no ML-DSA code (verified by source grep at commit 0085a1f).
  • Compression does not help: zlib-9 increases an ML-DSA-65 stand-in signature by 0.33% (MEASURED).

4. Fee market (count-based, not byte-based)

Reference fee 10 drops (postfiatd Config.h); base fee level 256 (FeeEscalation.md). Beyond the open-ledger limit, required fee level = median level × (transactions in open ledger / limit)² (quadratic). At limit 50, median level 256: 50 tx → 10 drops; 100 tx → 40 drops; 200 tx → 160 drops; 500 tx → 1,000 drops.

Base fee is identical for every scheme: 10 drops. A 3,309-byte ML-DSA-65 signature costs the same as a 64-byte Ed25519 signature at base load. Any claim that fees rise proportionally to signature size is wrong for this fee design.

Bytes per drop at base load (DERIVED): Ed25519 29.7; ML-DSA-65 546.1; SLH-DSA-256f 5,012.0.

Spamming 1 MB of ledger via ML-DSA-65 costs ~18.4x less than via Ed25519. The open-ledger limit counts transactions, not bytes, so a ledger can fill with far more bytes before quadratic escalation bites. A size-proportional fee would require a protocol change (new transaction-cost rule / amendment); no such amendment exists.

6. Mitigations

Compression — MEASURED, does not work

zlib-9 on deterministic stand-in signature bytes: ML-DSA-65 3,309 B → 3,320 B (+0.33%, larger); ML-DSA-44 +0.45%; SLH-DSA-256f +0.05%; Ed25519 64 B → 75 B (+17.19%, zlib framing overhead). Post-quantum signatures are near-maximally compressed lattice/hash vectors; no standardized ML-DSA compression exists in FIPS 204.

Hybrid / composite signatures — DERIVED, larger not smaller

ML-DSA-65+Ed25519 = 3,381 B (1.022x pure ML-DSA); ML-DSA-44+Ed25519 = 2,492 B (1.030x); ML-DSA-87+Ed25519 = 4,699 B (1.016x). A composite buys migration safety, not size. Status: draft-ietf-lamps-pq-composite-sigs-19, in IESG evaluation — not an RFC, not a NIST standard; composite ML-DSA offers EUF-CMA but not SUF-CMA.

Batching — SIMULATION ONLY

FIPS 204 (§5.3) specifies single-signature verification only; no batch-verification procedure exists. A hypothetical amortized factor of 0.8x (ASSUMED) would give ML-DSA-65 20,833 verifies/second/core (simulated). This is what a batch mechanism would need to deliver, not a measured gain. Parallel verification across cores is a real deployment lever (MODEL: linear scaling assumed).

REJECTED: BLS aggregation. BLS (RFC 9591) aggregates many signatures into one 96-byte aggregate, but it rests on elliptic-curve pairings (BLS12-381). Shor's algorithm breaks elliptic-curve discrete logarithms, so BLS offers no quantum resistance. It is a classical compression technique only.
REJECTED: post-quantum aggregation. No post-quantum signature aggregation scheme is a NIST standard. ML-DSA and SLH-DSA have no standardized aggregate form; proposals are research-stage.

Smaller parameter set

ML-DSA-44 instead of ML-DSA-65 saves 889 bytes per signature at security category 2 instead of 3 (DERIVED). Whether category 2 is acceptable is a policy decision. SLH-DSA-128s (32-byte public key, 7,856-byte signature) only makes sense where signing is rare.

Strongest project-grounded mitigation: off-consensus certificate lanes

The PostFiat FastPay series measures it: certificates ~15 KB (4× ML-DSA-65 signatures); cryptography ~2% of latency, network ~96%; owned-lane p50 55 ms (n=25,000). Settlement moves off the consensus path, so per-transaction signature bytes stop consuming consensus/ledger capacity.

7. Limitations

  • No per-transaction byte-size cap was found; admissibility of large post-quantum transactions is UNVERIFIED (needs a live-node test, not run here).
  • No native ML-DSA timing on validator hardware; throughput figures are a calibrated MODEL.
  • No published SLH-DSA verification time in the source set; SLH-DSA excluded from the cost model.
  • FeeEscalation.md contradicts itself on the minimum lastLedgerMedianFeeLevel (128,000 vs 500) — unresolved.
  • Workload (1,500 TPS, 4-second ledgers) is a stated assumption from the postfiatd README, not a measurement.
